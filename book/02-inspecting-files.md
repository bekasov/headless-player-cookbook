# Глава 2. Смотрим внутрь файла из консоли

Главное правило этой главы: **о файле нельзя рассуждать, на него нужно смотреть.**
На стенде мы потратили немало времени, рассуждая о «10-битном» файле, который на деле был
8-битным. Одна команда сэкономила бы полдня.

Основной инструмент здесь `ffprobe` из пакета ffmpeg. На сервере он, скорее всего, уже
есть (`command -v ffprobe`). Второй взгляд, глазами GStreamer, работает прямо на плате,
где ffmpeg с нужными возможностями может и не быть.

---

## Рецепт 2.1. Быстрый общий взгляд

**Задача.** Узнать, что за контейнер, какая длительность и какие потоки в файле.

**Решение.**

```
[сервер]
ffprobe -hide_banner "фильм.mkv"
```

**Как это работает.** Без дополнительных ключей `ffprobe` печатает сводку: строка
`Input #0, matroska,webm` (контейнер), `Duration` (длительность), затем строки
`Stream #0:0: Video: hevc (Main 10)...`, `Stream #0:1: Audio: aac...`.

**Подводные камни.** Вывод идёт в stderr, поэтому для `grep` нужен `2>&1`:

```
[сервер]
ffprobe -hide_banner "фильм.mkv" 2>&1 | grep -E 'Input|Duration|Stream'
```

## Рецепт 2.2. Только нужные поля видео

**Задача.** Получить кодек, профиль, разрешение, частоту кадров и формат пикселей в виде,
удобном для скриптов.

**Решение.**

```
[сервер]
ffprobe -v error -select_streams v:0 \
  -show_entries stream=codec_name,profile,pix_fmt,width,height,r_frame_rate \
  -of default=nw=1 "фильм.mkv"
```

Пример ответа с нашего стенда:

```
codec_name=hevc
profile=Main 10
width=1920
height=1080
pix_fmt=yuv420p10le
r_frame_rate=25/1
```

**Как это работает.** `-v error` убирает болтовню, `-select_streams v:0` берёт первый
видеопоток, `-show_entries` перечисляет поля, `-of default=nw=1` печатает их без
заголовков секций.

**Подводные камни.** `ffprobe` принимает **один файл за вызов**. Два файла в одной команде
дадут ошибку «Argument ... provided as input filename, but ... was already specified».
Для нескольких файлов используйте цикл.

## Рецепт 2.3. Сколько в файле реальных кадров

**Задача.** Убедиться, что файл не пустой и не битый (особенно если вы его только что
вырезали или перекодировали).

**Решение.**

```
[сервер]
ffprobe -v error -select_streams v:0 -count_frames \
  -show_entries stream=nb_read_frames:format=duration \
  -of default=nw=1 "кусок.mkv"
```

**Как это работает.** `-count_frames` заставляет `ffprobe` действительно декодировать поток
и посчитать кадры. Для 60 секунд при 25 кадрах/с должно быть около 1500.

**Подводные камни.** Без `-count_frames` вы увидите только заявленные параметры потока.
Пустой файл с правильным заголовком выглядит так же, как полный.

---

## Рецепт 2.4. Цветовые метки

**Задача.** Узнать, какую цветовую схему заявляет файл (рецепт 1.5).

**Решение.**

```
[сервер]
ffprobe -v error -select_streams v:0 \
  -show_entries stream=color_space,color_transfer,color_primaries,color_range \
  -of default=nw=1 "фильм.mkv"
```

**Как это работает.** Пустые значения или `unknown` означают, что меток нет, и
проигрыватель будет угадывать. `smpte2084` в `color_transfer` означает HDR10 (PQ),
`arib-std-b67` означает HLG.

---

## Рецепт 2.5. Как перемешаны звук и видео

**Задача.** Узнать, насколько звук в файле опережает видео. Это нужно, чтобы понять, хватит
ли проигрывателю очередей (глава 10).

**Решение.**

```
[сервер]
ffprobe -v error -show_entries packet=stream_index,pts_time -of csv=p=0 \
  -read_intervals %+3 "кусок.mkv" | grep -n '^0,' | head -n 1
```

На стенде ответ был `51:0,1.120000`.

**Как это работает.** Команда печатает пакеты первых трёх секунд в порядке, в котором они
лежат в файле: номер потока и метку времени. `grep -n '^0,'` находит первый видеопакет
(поток 0). Число до двоеточия минус один это сколько звуковых пакетов идёт раньше
первого видео. Один пакет AAC при 48 кГц длится 1024/48000 ≈ 21 мс, так что 50 пакетов
это около 1,07 с опережения.

**Подводные камни.** Номера потоков в вашем файле могут быть другими: сначала посмотрите
рецепт 2.1.

## Рецепт 2.6. Шумный файл MPEG-TS

**Задача.** Разобраться, нормален ли файл, из-за которого `ffprobe` сыплет сотнями строк
`non-existing PPS 0 referenced` и `no frame!`.

**Решение.** Не читать лог, а проверить результат:

```
[сервер]
ffprobe -hide_banner "запись.ts" 2>&1 | grep -vE 'non-existing PPS|no frame|Last message repeated' | head -n 25
```

а затем вырезать кусок и посчитать в нём кадры (рецепт 2.3).

**Как это работает.** Записи с телевидения и потоковых сервисов (MPEG-TS) часто начинаются
с середины потока. Декодер ждёт первого набора параметров (PPS/SPS) и до него ругается. На
стенде одинаковое число ошибок (53) было и при перемотке до `-i`, и после неё: это была
начальная пачка при пробе файла, а не порча нужного отрезка. Кадры в вырезанном куске
оказались целы (ровно 1500).

**Подводные камни.** Конец лога легко принять за доказательство того, что ошибки идут
«всё время», хотя лог может состоять только из начальной пачки. Проверяйте файл-результат,
а не хвост лога.

## Рецепт 2.7. Тот же взгляд глазами GStreamer

**Задача.** Посмотреть параметры потока на самой плате, без ffmpeg.

**Решение.**

```
[плата]
timeout 5 stdbuf -oL gst-launch-1.0 -v filesrc location=$HOME/test/film.mkv ! parsebin ! fakesink \
  > $HOME/test/parse.log 2>&1
grep -m 1 'video/x-h265' $HOME/test/parse.log | tr ',' '\n' | \
  grep -E 'colorimetry|profile|bit-depth|chroma|framerate|width|height'
```

Пример ответа:

```
 profile=(string)main
 width=(int)1440
 height=(int)1080
 framerate=(fraction)60/1
 colorimetry=(string)0:4:8:3
 chroma-format=(string)4:2:0
 bit-depth-luma=(uint)8
```

**Как это работает.** `parsebin` подбирает демультиплексор и разборщик потока, а ключ `-v`
заставляет GStreamer печатать «подписи» (caps) на каждом соединении. Поле `colorimetry`
в числовом виде читается как «диапазон:матрица:передача:первичные»:

| Позиция | Значение `0:4:8:3` |
|---|---|
| Диапазон | 0 = не указан (1 = полный, 2 = ограниченный) |
| Матрица | 4 = BT.601 (3 = BT.709, 6 = BT.2020) |
| Передача | 8 = гамма 2,8 (BT.470BG) (5 = BT.709) |
| Первичные | 3 = BT.470BG (1 = BT.709, 7 = BT.2020) |

Значения взяты из заголовка `video-color.h` GStreamer.

**Подводные камни.** `stdbuf -oL` нужен потому, что `timeout` убивает процесс сигналом, и
всё, что программа накопила в буфере вывода, теряется. С `stdbuf -oL` вывод сбрасывается
после каждой строки (подробнее в рецепте 6.3).

## Рецепт 2.8. Сделать тестовые файлы нужного формата

**Задача.** Получить короткие файлы с заранее известными параметрами: 8-битный и 10-битный
H.265 со звуком AAC.

**Решение.**

```
[сервер]
set src "путь/к/фильму.ts"
ffmpeg -hide_banner -loglevel error -stats -ss 300 -t 60 -i $src \
  -map 0:v:0 -map "0:a:0?" -c:v libx265 -preset fast -crf 20 -pix_fmt yuv420p10le \
  -c:a aac -b:a 192k -ac 2 ~/t-hevc10-1080p.mkv
ffmpeg -hide_banner -loglevel error -stats -ss 300 -t 60 -i $src \
  -map 0:v:0 -map "0:a:0?" -c:v libx265 -preset fast -crf 20 -pix_fmt yuv420p \
  -c:a aac -b:a 192k -ac 2 ~/t-hevc8-1080p.mkv
```

Затем проверка рецептом 2.2 (профиль) и рецептом 2.3 (число кадров).

**Как это работает.** `-ss` до `-i` перематывает быстро (по ключевым кадрам), `-t 60` берёт
минуту, `-map 0:v:0` и `-map "0:a:0?"` выбирают первое видео и первый звук, если он есть
(вопросительный знак делает звук необязательным). `-pix_fmt` задаёт разрядность, а значит,
и профиль.

**Подводные камни.**
- `libx265` с заглядыванием вперёд задерживает первые видеокадры. В наших файлах звук
  опережал видео примерно на секунду, и это сломало проигрывание (глава 10). Настоящие
  фильмы бывают перемешаны ровнее.
- Синтетический поток, сделанный `x265enc` из GStreamer в режиме ultrafast прямо на плате,
  драйвер отверг (`VIDIOC_S_EXT_CTRLS failed: Invalid argument`), хотя файлы от `libx265`
  принял. Причину мы не нашли. Для проверок лучше брать материал из настоящих фильмов.

## Рецепт 2.9. Сделать клипы-измерители

**Задача.** Получить короткие клипы, каждый из которых отвечает на один вопрос: сколько
кадров в секунду декодер тянет при данном размере кадра, правильно ли обрезается кадр по
краям, откуда подёргивание (от конвейера или от частоты экрана).

**Решение.** Клипы делаются на сервере и переносятся на плату под другими именами. Пример
со второго стенда (Banana Pi M1, H.264; отрезок фильма 1920x800 уже лежит на сервере):

```
[сервер]
cd ~/bananapi
set src film_cut60_from_bpi.mp4
ffmpeg -hide_banner -i $src -an -vf scale=1920:1080 -c:v libx264 -profile:v high -level 4.1 \
  -pix_fmt yuv420p -refs 1 -bf 2 -b:v 6300k -maxrate 8000k -bufsize 12000k srvtest_1080p.mp4
ffmpeg -hide_banner -i $src -an -vf scale=1280:720 -c:v libx264 -profile:v high -level 4.1 \
  -pix_fmt yuv420p -refs 1 -bf 2 -b:v 6300k -maxrate 8000k -bufsize 12000k srvtest_720p.mp4
ffmpeg -hide_banner -f lavfi -i testsrc2=size=1920x1080:rate=24 \
  -vf "drawbox=x=0:y=0:w=iw:h=ih:color=red:t=4" -t 15 -c:v libx264 -profile:v high -level 4.1 \
  -pix_fmt yuv420p -b:v 4000k -maxrate 6000k -bufsize 8000k -g 48 -bf 2 -an srv_edge1080.mp4
ffmpeg -hide_banner -f lavfi -i testsrc2=size=1280x704:rate=24 -t 30 -c:v libx264 -profile:v high \
  -level 4.1 -pix_fmt yuv420p -b:v 4000k -maxrate 6000k -bufsize 8000k -g 48 -bf 2 -an srv_tc24.mp4
ffmpeg -hide_banner -f lavfi -i testsrc2=size=1280x704:rate=30 -t 30 -c:v libx264 -profile:v high \
  -level 4.1 -pix_fmt yuv420p -b:v 4000k -maxrate 6000k -bufsize 8000k -g 60 -bf 2 -an srv_tc30.mp4
scp srvtest_1080p.mp4 coop@адрес-платы:~/test/onboard_1080p.mp4
```

(Остальные клипы переносятся так же, каждый под своим именем.)

**Как это работает.**
- **Лестница разрешений.** Клипы 1080p и 720p сделаны из одного отрезка с одинаковыми
  параметрами кодирования, поэтому разница в скорости декодера относится только к размеру
  кадра (рецепт 6.7). Растягивание 1920x800 до 1920x1080 искажает картинку, зато все
  макроблоки кадра остаются «живыми», как в настоящем фильме.
- **Рамка.** `drawbox` рисует красную рамку толщиной 4 пикселя по краю кадра 1920x1080.
  Декодер хранит такой кадр высотой 1088; если обрезка до 1080 сделана правильно, нижняя
  линия рамки видна у самого края экрана (рецепт 7.10).
- **Пара 24 и 30 кадров/с.** На экране 60 Гц 30 кадров показываются ровно (каждый два
  обновления), а 24 по очереди два и три обновления. Если 30 идёт гладко, а 24 с ритмичным
  подёргиванием, виноват каденс экрана, а не конвейер. Размер 1280x704 кратен 32 по обеим
  сторонам, поэтому ни выравнивания, ни обрезки в этих клипах нет.

**Подводные камни.**
- `ffprobe` показал у клипа 1080p `coded_height=1080`, хотя декодер хранит такой кадр
  высотой 1088. О выравнивании по `ffprobe` судить нельзя: спрашивайте драйвер (рецепт 5.7).
- В выводе `ffprobe` у новых клипов не оказалось поля `refs`, поэтому применилось ли
  `-refs 1`, мы не знаем. Для замера скорости это неважно.
- У `testsrc2` у левого края своя красная полоса, на её фоне рамку слева почти не видно.
