# Глава 4. Образ, проверка, запись, первый вход

Эта глава о самой опасной команде в книге. `dd` молча пишет туда, куда сказали, и если
сказали «на системный диск сервера», он туда и запишет. Поэтому рецепты здесь медленнее,
чем могли бы быть, и это нарочно.

---

## Рецепт 4.1. Скачать действительно последний образ

**Задача.** Получить свежую сборку и знать её точное имя.

**Решение.**

```fish
# [сервер]
mkdir -p ~/armbian-zero2; cd ~/armbian-zero2
set f Armbian_community_26.11.0-trunk.108_Orangepizero2_trixie_current_6.18.57_minimal.img.xz
curl -L -o $f     https://dl.armbian.com/orangepizero2/Trixie_current_minimal
curl -L -o $f.sha https://dl.armbian.com/orangepizero2/Trixie_current_minimal.sha
curl -L -o $f.asc https://dl.armbian.com/orangepizero2/Trixie_current_minimal.asc
```

**Как это работает.** Ссылка `Trixie_current_minimal` это псевдоним «самое свежее». Сервер
перенаправляет его на зеркало с настоящим именем файла, и это имя видно по
перенаправлению. Мы сохраняем все три файла под одним базовым именем, потому что `gpg`
ищет подписанный файл по имени подписи без `.asc`.

> [!warning] Подводные камни
> Слово `trunk` в имени означает сборку из основной ветки разработки,
> а не фиксированный выпуск. Для экспериментов это нормально, для «эталона» стоит записать
> номер сборки.

## Рецепт 4.2. Проверить целостность и подлинность

**Задача.** Убедиться, что файл не повреждён и выпущен Armbian, а не зеркалом.

**Решение.**

```fish
# [сервер]
cat $f.sha
sha256sum $f
gpg --keyserver hkp://keyserver.ubuntu.com --recv-key DF00FAF1C577104B50BF1D0093D6889F9F0E78D5
gpg --verify $f.asc
```

**Как это работает.**

- Хэш из `.sha` и вычисленный должны совпасть посимвольно. Это защищает от порчи при
  скачивании.
- `gpg --verify` проверяет подпись. Смотрите строку `Primary key fingerprint`: она должна
  совпасть с отпечатком из документации Armbian. Имя в подписи можно подделать, отпечаток нет.
- Предупреждение `This key is not certified with a trusted signature` нормально: оно лишь
  означает, что вы лично не заверяли этот ключ.

> [!warning] Подводные камни
> Не используйте `sha256sum -c`: в файле `.sha` может стоять путь из
> сборочной среды, и проверка «не найдёт» файл. Сравнивайте хэши глазами или одной
> строкой fish:
>
> ```fish
> # [сервер]
> grep -qi (sha256sum $f | cut -d' ' -f1) $f.sha; and echo совпадает; or echo 'НЕ совпадает'
> ```

## Рецепт 4.3. Найти карту и не перепутать её с диском

**Задача.** Определить имя устройства карты памяти безошибочно.

**Решение.** Посмотреть список дисков **до** и **после** вставки карты:

```fish
# [сервер]
lsblk -o NAME,SIZE,TYPE,RM,TRAN,MODEL,MOUNTPOINTS
# вставить карту, подождать пару секунд
lsblk -o NAME,SIZE,TYPE,RM,TRAN,MODEL,MOUNTPOINTS
lsblk -o NAME,SIZE,FSTYPE,LABEL,RM,MOUNTPOINTS /dev/sdf
```

**Как это работает.** Карта это устройство, которое появилось во втором списке и которого
не было в первом. Подтверждают: размер (16 ГБ карта видна как 14,8 ГБ), `RM=1`
(съёмное), `TRAN=usb` (через считыватель). Последняя команда показывает, что сейчас на
карте и не примонтирована ли она.

> [!warning] Подводные камни
> - Имя `sdf` не постоянное. После повторной вставки или перезагрузки оно может стать другим.
>   Проверяйте каждый раз.
> - На машине с несколькими дисками ошибка в одной букве стоит всех данных.

## Рецепт 4.4. Записать образ

**Задача.** Распаковать образ прямо на карту, не занимая места на диске.

**Решение.**

```fish
# [сервер]
xzcat $f | sudo dd of=/dev/sdf bs=4M conv=fsync status=progress
sync
lsblk -o NAME,SIZE,FSTYPE,LABEL /dev/sdf
```

**Как это работает.** `xzcat` распаковывает поток в стандартный вывод, `dd` пишет его на
устройство блоками по 4 МБ, `conv=fsync` гарантирует, что данные действительно легли на
карту до выхода. На стенде 1,6 ГБ записались за 131 секунду (около 12 МБ/с). После
записи на карте один раздел примерно на 1,5 ГБ: Armbian расширит его на всю карту при
первом запуске.

> [!warning] Подводные камни
> - Не распаковывайте образ в `/tmp`, если `/tmp` у вас в памяти (tmpfs).
> - Если раздел карты примонтирован, сначала `sudo umount`.
> - Считыватель можно не выдёргивать между картами. Вынимайте карту, только когда индикатор
>   не мигает и после `sync`.

## Рецепт 4.5. Первый вход

**Задача.** Загрузить плату и войти в систему.

**Решение.** Вставить карту, подключить HDMI, клавиатуру, Ethernet и **питание последним**
(5 В через USB-C, не меньше 2 А). Подождать до двух минут. Дальше два пути:

- **На мониторе** Armbian сам входит под root и запускает мастер: пароль root, обычный
  пользователь с sudo, язык. Пароли набирайте латиницей: на этом этапе раскладка QWERTY.
- **По SSH**, если экран не показывает: `ssh root@адрес-платы`, пароль `1234`, и тот же
  мастер.

**Как это работает.** При входе Armbian показывает баннер. Из него сразу видно много
полезного:

```text
 v26.11 rolling for Orange Pi Zero2 running Armbian Linux 6.18.57-current-sunxi64
 Packages:     Debian stable (trixie)
 Updates:      Kernel upgrade enabled and 4 packages available for upgrade
 Memory usage: 14% of 969M
 Usage of /:   10% of 15G
```

Раздел расширился до 15 ГБ, памяти 969 МБ (столько видит система из 1 ГБ).

> [!warning] Подводные камни
> - Монитор может не переключаться сам на «неактивный» вход: переключите вручную.
> - **Не обновляйтесь сразу.** Сначала зафиксируйте, как ведёт себя система «как есть»:
>   если ядро обновится посреди проверок, вы не поймёте, что на что повлияло. Посмотреть,
>   что предлагается обновить, можно безопасно:
>
> ```bash
> # [плата]
> apt list --upgradable
> ```

## Рецепт 4.6. Не потерять долгую работу при обрыве SSH

**Задача.** Запустить сборку или долгий тест так, чтобы обрыв связи его не убил.

**Решение.**

```bash
# [плата]
tmux new -s build
# ... долгие команды ...
# отсоединиться: Ctrl+b, затем d
tmux attach -t build
```

> [!warning] Подводные камни
> Если при вставке команды первая строка выглядит как
> `^[[200~rm ...` и оболочка пишет «command not found», это обрывки «вставки в скобках»
> терминала. Команду можно просто повторить.

## Рецепт 4.7. Поставить предохранитель на `dd`

**Задача.** Сделать так, чтобы запись не началась, если имя устройства вдруг указывает не на
карту.

**Решение.** Обернуть запись проверками. Пример со второго стенда (карта 64 ГБ в
считывателе, оболочка fish):

```fish
# [сервер]
set f ~/bananapi/Armbian_26.8.1_Bananapi_trixie_current_6.18.43_minimal.img.xz
if test -f $f; and test (cat /sys/block/sdf/removable) = 1; and test (lsblk -bndo SIZE /dev/sdf) -gt 50000000000; and test (lsblk -bndo SIZE /dev/sdf) -lt 70000000000; and test -z (lsblk -nlo MOUNTPOINTS /dev/sdf | string join '')
    xzcat $f | sudo dd of=/dev/sdf bs=4M conv=fsync status=progress
    sync
else
    echo ABORT: guard failed
end
lsblk -o NAME,SIZE,FSTYPE,LABEL,MOUNTPOINTS /dev/sdf
```

Ответ второго стенда:

```text
1421869056 bytes (1.4 GB, 1.3 GiB) copied, 39.997 s, 35.5 MB/s
sdf     58.3G
└─sdf1   1.3G ext4   armbi_root
```

**Как это работает.** Запись начинается, только если выполнено всё сразу:

- файл образа существует;
- ядро считает устройство съёмным (`/sys/block/sdf/removable` равно 1);
- размер устройства в байтах попадает в коридор вокруг размера карты (карту 64 ГБ
  `lsblk` показывает как 58,3 ГиБ): `-b` даёт байты, `-n` убирает заголовок, `-d` не
  показывает разделы;
- ни один раздел не примонтирован.

Если хоть одна проверка не прошла, выводится `ABORT`, и на устройство ничего не пишется.

> [!warning] Подводные камни
> - Предохранитель не заменяет сравнения `lsblk` до и после вставки (рецепт 4.3). Он ловит
>   другую ошибку: имя, которое поменялось между проверкой и записью.
> - Некоторые считыватели сообщают `removable=0`. Тогда предохранитель честно откажет;
>   разберитесь по `lsblk -o NAME,SIZE,TYPE,RM,TRAN`, а не выключайте проверку.
> - Коридор размера подбирайте под свою карту.

## Рецепт 4.8. Записать эталон, даже если система уже обновлена

**Задача.** Понять, обновлялась ли система, и зафиксировать точные версии, с которыми
ведутся проверки.

**Решение.**

```bash
# [плата]
cat /etc/armbian-release
uname -a
dpkg -l | grep -E 'linux-image|linux-dtb|armbian-'
sudo grep -E '^(Start-Date|Commandline|End-Date)' /var/log/apt/history.log
```

На втором стенде образ назывался `Armbian_26.8.1_..._current_6.18.43_minimal.img.xz`, а
система при первом входе по SSH уже показывала `v26.8.3` и ядро `6.18.44-current-sunxi`:
её обновили до проверок. Эталоном стали установленные пакеты:

```text
linux-image-current-sunxi         26.8.3   ... kernel image 6.18.44-current-sunxi
linux-dtb-current-sunxi           26.8.3
armbian-bsp-cli-bananapi-current  26.8.3
armbian-firmware                  26.8.3
```

**Как это работает.** Первый признак обновления: версия в баннере или в
`/etc/armbian-release` не совпадает с именем записанного образа. Журнал `apt` показывает,
когда и какой командой ставились пакеты. Обновление само по себе не беда (рецепт 4.5
советует отложить его ради чистоты сравнения); беда, если версия неизвестна.

> [!warning] Подводные камни
> - Записывайте версии в заметки сразу: после следующего `apt upgrade` восстановить, с чем
>   вы мерили, будет нельзя.
> - Пакеты, поставленные для проверок (`v4l-utils`, `ffmpeg`, пакеты GStreamer), тоже часть
>   эталона. Перед установкой смотрите строку `Summary` у `apt`: `Removing: 0` и как можно
>   меньше обновлений.
